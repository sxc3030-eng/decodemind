# DecodeMind V1 — Sprint Plan

> **For agentic workers:** Each sprint below gets its own detailed task plan when work starts. This document is the V1 roadmap, not a per-step execution checklist.
>
> Use `superpowers:writing-plans` to expand a sprint into tasks; use `superpowers:subagent-driven-development` to execute.

**Goal:** Ship DecodeMind V1 — a free, privacy-first browser code scanner with sectioned plain-language reports for security, bugs, logic, and quality.

**Foundation:** Phase 0 spike on branch `phase-0` (23+ commits). Spec at `docs/superpowers/specs/2026-05-18-decodemind-design.md` revised with Phase 0 lessons.

**Tech Stack:** React 18 + Vite 5 + TypeScript 5.9 + Tailwind 3, Ruff WASM, ESLint browserify, ast-grep WASM + tree-sitter grammars, Prettier 3.8 standalone, WebLLM 0.2.83 + Qwen 2.5 Coder (tiered 1.5B / 3B / 7B), File System Access API, OPFS + IndexedDB + Cache API, Cloudflare Pages.

**Estimated timeline:** 13 weeks solo (8 sprints, mostly 1.5-2 weeks each). 6-8 weeks for a rough usable MVP if scope is cut to security + bugs categories only.

**Branch strategy:** keep `phase-0` as the spike reference. Create `v1` branch off `master` (or off `phase-0` after final review). Each sprint gets a feature branch from `v1` — short-lived, merged via PR (even though it's solo — discipline + CV signal).

## Sprint 1 — Foundation cleanup & V1 scaffold (1 week)

**Goal:** Promote the spike's reusable code (`src/lib/`, `src/workers/`) into V1, remove spike-only code, fix the V1-blocking issues caught by the final reviewer.

**Key tasks:**

1. **Branch + folder restructure**
   - Create `v1` branch off `phase-0` (or off `master` if we want a clean slate — decide based on whether the spike's lib code is V1-ready)
   - Decide: keep `src/spike/` as a reference under `src/spike/` (read-only), OR move spike contents to `src/v1-reference/`, OR delete entirely (cleanest)
   - Adopt the V1 file structure from the spec (see section 9)

2. **Fix V1-blocking issues from Phase 0 final review**
   - Install `eslint` as devDep, replace `as never` cast in `src/workers/eslint.worker.ts`
   - Switch `requestAdapterInfo()` → `adapter.info` getter in `src/lib/llm/loader.ts`
   - Audit all `new URL(..., import.meta.url)` usages for relative-literal compliance
   - Run `npm run build` and verify per-worker chunks emit correctly (each worker as a separate `*.worker-*.js`)

3. **State management foundation**
   - Add Zustand store(s) — match GeniA conventions (per `active_projects.md` memory)
   - Add TanStack Query if/where async caching pays for itself (probably overkill for V1)
   - Wire up React Router (or just useState routing — V1 is single-page)

4. **Service worker + offline foundation**
   - Add Vite PWA plugin (`vite-plugin-pwa`)
   - Configure Workbox to cache the static assets + Hugging Face model URLs
   - Verify "site works fully offline after first load" claim from spec section 6 non-functional

5. **Quality gates**
   - Set up Prettier + ESLint for the V1 source tree itself (with `eslint` now a devDep)
   - Add a `lint` script to package.json
   - Pre-commit hook (Husky) running `npm run typecheck && npm run lint && npm test` — minimal, non-invasive

**Deliverable:** `v1` branch with the spike's lib/worker code, broken-worker-URLs fixed, ESLint configured, Husky hook, basic Zustand store skeleton. Ready for Sprint 2 features.

**Exit criteria:** `npm run build` emits N separate worker chunks; `npm run preview` loads the page in Firefox (degraded) and Chrome (full) without console errors; pre-commit hook blocks a broken commit.

## Sprint 2 — File picker + ignore patterns production-grade (2 weeks)

**Goal:** Turn the spike's folder picker into a polished V1 feature with project-configurable ignore patterns and auto-generated-file detection.

**Key tasks:**

1. **Productized folder picker**
   - Polished UI: drag-and-drop zone OR "Pick folder" button, file count + size preview before scan
   - Persistent permissions (handle `queryPermission` / `requestPermission` flows)
   - Save last-scanned folder handle in IndexedDB; on revisit, offer "Re-scan {last folder}"
   - Firefox/Safari fallback: `<input webkitdirectory>` + ZIP download of patches at the end

2. **`.decodemind-ignore` file support**
   - Read `.decodemind-ignore` from the picked folder root (if present)
   - Parse gitignore-syntax (use the `ignore` npm package — battle-tested)
   - Merge with built-in IGNORED_DIRS list
   - UI shows: "X built-in patterns + Y from .decodemind-ignore"

3. **Auto-generated detection productized**
   - Extend the Phase 0 heuristic with more markers (config files, IDE-generated, lock files patterns)
   - Make it skippable via a checkbox "Include auto-generated files"
   - Show count in scan summary

4. **Project size handling**
   - Pre-scan: walk the tree to count matched files BEFORE reading content
   - If > 2000 files: confirm modal with breakdown by extension and suggested ignore additions
   - Streaming scan (scan as you walk, show partial results) — research feasibility

5. **Worker pool**
   - Today the folder scanner uses one worker per scanner type. For V1, pool workers (2-4 per type) and parallelize across files
   - Measure speedup vs sequential — only ship if > 2× faster on a 500-file project

**Deliverable:** Production-grade folder picker with `.decodemind-ignore`, auto-gen detection, and pooled workers.

**Exit criteria:** Scanning a 500-file mixed-language repo completes in < 30 s on Intel i5; ignore patterns work from a `.decodemind-ignore` file; Safari/Firefox users get a working (read-only + ZIP-download) experience.

## Sprint 3 — ast-grep grammar pipeline + first 30 rules (2 weeks)

**Goal:** Make ast-grep actually work end-to-end with tree-sitter grammars, and seed the rule library with the highest-value 30 rules.

**Key tasks:**

1. **Vite plugin for grammar files**
   - Find the right tree-sitter grammar source (npm packages: `tree-sitter-python`, `tree-sitter-typescript`, `tree-sitter-javascript`, `tree-sitter-html`, `tree-sitter-css`)
   - Write a Vite plugin that copies each grammar's `.wasm` to `public/tree-sitter-<lang>.wasm` at build time
   - Verify the ast-grep worker can `registerDynamicLanguage` and `parse` correctly

2. **ast-grep rule loader**
   - Replace the spike's hand-rolled `parseRuleYaml` with a proper YAML parser (`yaml` npm package)
   - Validate rules against ast-grep's schema (use ast-grep's own validation if it exposes one)
   - Cache parsed rules in memory

3. **First 30 rules (security-focused for V1 launch)**
   - **`ws-auth-*`** family (5 rules) — WebSocket origin/token/max_size patterns. Source: NetGuardPro `sentinel/cortex.py` audit findings.
   - **`crypto-*`** family (8 rules) — weak hash algorithms, hardcoded secrets, key rotation, file perms. Source: NetGuardPro `vpnguard/`, `permissions.py`.
   - **`injection-*`** family (10 rules) — `shell=True`, path traversal, SQL concatenation, command injection variants, `eval`. Source: NetGuardPro `vpnguard/vpnguard.py`, CodeHalu, Veracode 2025.
   - **`xss-*`** family (5 rules) — `innerHTML` with user input, missing escape helpers. Source: NetGuardPro `netguard_dashboard.html` audit.
   - **`llm-hallucination-*`** family (2 starter rules) — fake pandas methods (the existing one) + fake React hooks.

4. **Rule testing infrastructure**
   - Per-rule fixtures: input source + expected matches
   - Vitest harness that loads ast-grep + runs each rule against its fixture
   - CI runs the harness on every push

5. **Built-in plain-English dictionary**
   - For each of the 30 rules, write a 2-3 sentence plain explanation
   - Stored as a JSON map in `src/v1/rules/explanations.{en,fr}.json`
   - Used by the degraded mode (no LLM) and as the LLM fallback

**Deliverable:** ast-grep fully wired with grammars for Python/TS/JS/HTML/CSS; 30 custom rules with tests; plain-English dictionary for all 30 rules in EN + FR.

**Exit criteria:** Re-scanning the `mamy` project finds the original `shell=True` finding via the new ast-grep rule (not just Ruff's S602); all 30 rules have ≥ 1 positive test fixture and ≥ 1 negative fixture; CI green.

## Sprint 4 — WebLLM tier UX + translation cache (2 weeks)

**Goal:** Productize the WebLLM integration with proper UX for tier selection, model download progress, and translation caching.

**Key tasks:**

1. **First-visit tier selection UX**
   - Modal on first scan: explain tiers (Quick / Better / Best) with disk + GPU recommendations
   - Auto-recommend based on `detectAdapter()` (already implemented in the spike's `pickDefaultTier`)
   - "Skip download — use built-in explanations" option (degraded mode)
   - Saved choice persisted in IndexedDB

2. **Model download progress UI**
   - Progress bar showing % + downloaded MB / total MB + ETA
   - Pause/resume support (verify WebLLM supports it; if not, document)
   - Resume on refresh if interrupted

3. **OPFS for model weights**
   - Verify WebLLM uses OPFS by default in 0.2.83+ (per Phase 0 research it can be configured via `useIndexedDBCache: false`)
   - If not, configure it explicitly
   - Verify second visit loads in < 5 seconds from cache

4. **Translation cache (IndexedDB)**
   - Schema: `{ key: ruleId + normalizedCode, language, content, model_tier, created_at }`
   - `normalizedCode` per spec section 4: strip whitespace, comments, replace string/number literals with placeholders, replace SCREAMING_SNAKE identifiers with `<CONST>`
   - LRU eviction at ~50 MB cache size
   - "Clear cache" in settings, shows current cache size

5. **Translation pipeline**
   - Production version of `translateFinding`: batch 8 findings per LLM call (already in spike's design)
   - Streaming UI: show "Translating finding X of Y…" while running
   - Graceful failure: if any single batch errors, show the raw rule message for those findings (don't fail the whole scan)

6. **"Second opinion" via user's API key** (DEFER if time-pressed — moved to V2 in spec)
   - This was deferred in Phase 0 review; reaffirm V2 unless tier 1.5B turns out too weak

**Deliverable:** Productized WebLLM with tier UX, OPFS storage, IndexedDB translation cache, batched translation.

**Exit criteria:** First-load time on Quick tier matches Phase 0 measurement; cache hit rate after 2 scans of the same project ≥ 60%; cold scan of 10k LOC default tier in ≤ measured Phase 0 budget.

## Sprint 5 — Sectioned report UI + severity routing (2 weeks)

**Goal:** Implement the sectioned report (Security / Bugs / Logic / Quality) with the severity routing that Phase 0 proved is non-negotiable.

**Key tasks:**

1. **Sectioned report component**
   - Four collapsible sections (default: Security expanded, Bugs expanded, Logic collapsed, Quality collapsed)
   - Each section: count badge, severity tally (critical / important / minor)
   - Empty state per section ("No security findings 🎉")

2. **Per-finding card**
   - Severity badge (color-coded)
   - File path + line range (click to expand a code excerpt panel)
   - Plain-language explanation (from translation cache or built-in dictionary)
   - "Why it matters" + "How to fix" if available
   - Action buttons (Apply / Ignore / Details — apply comes in Sprint 6)

3. **Filtering + sorting**
   - Filters: severity, category, file path glob, "auto-fixable only"
   - Sort: by severity (default), by file, by rule
   - Persist filters per scan in IndexedDB

4. **Noise score in scan summary**
   - Top of report: `X findings · noise score: Y%`
   - If noise > 60%, show a callout: "Most findings are style. Consider adding {top-noisy-dir} to .decodemind-ignore"
   - Click → opens ignore-pattern editor

5. **History page**
   - Last 10 scans (metadata only — file count, finding count, timestamp, project name from folder)
   - Click → load that scan's report from IndexedDB
   - "Clear history" button

6. **Settings page**
   - UI language (FR/EN)
   - Tier (Quick / Better / Best / Skip)
   - Cache management (size, clear)
   - Strictness mode (Strict / Standard / Permissive — maps to ast-grep rule filtering)
   - Theme (dark / light — currently dark only, V1 keeps dark, add light if time)

**Deliverable:** Full sectioned report UI with filters, noise score, history, settings.

**Exit criteria:** First-time user finds the 4 actionable mamy findings without scrolling past noise; filters work; history persists across browser restarts.

## Sprint 6 — Auto-fix L1/L2 + backup + remaining 50-120 rules (2 weeks)

**Goal:** Make findings actionable — one-click apply for mechanical and suggested fixes, with safety net.

**Key tasks:**

1. **L1 auto-fix application**
   - Wire each scanner's auto-fix output (Ruff's `fix`, ESLint's `fix`, Prettier's full reformat) to a file-rewrite action
   - Before write: copy original to `.decodemind-backup/<ISO-timestamp>-<filename>`
   - Update IndexedDB scan record with applied/ignored status

2. **L2 suggested fix**
   - Show diff before applying (Monaco diff editor OR a simple textarea-based diff component — pick lighter)
   - "Apply" / "Edit" / "Cancel" actions
   - Same backup mechanism

3. **Undo last fix**
   - Per-scan button: restore the last-fixed file from backup
   - Per-finding ignore: persist in IndexedDB; doesn't re-surface next scan

4. **Backup management**
   - Settings: list backups by date, "Clear backups older than 7 days"
   - Auto-cleanup with consent on first apply
   - Offer to add `.decodemind-backup/` to user's `.gitignore` on first apply

5. **Remaining 50-120 ast-grep rules**
   - **Bug-detection family** (~25 rules): off-by-one, missing `await`, unused `except`, type confusion, deprecated APIs (per CodeHalu data + LLM-hallucination research)
   - **Logic family** (~15 rules): mutex/lock without unlock, missing close, unhandled promise rejection
   - **Quality family** (~30 rules): code complexity, dead code beyond linter coverage, magic numbers, naming
   - **LLM-hallucination expansion** (~30 rules): library function hallucinations (pandas, numpy, requests), import hallucinations, fabricated config keys
   - Each rule: positive + negative fixture, plain-English explanation in EN + FR

6. **Rule severity tuning**
   - Strict / Standard / Permissive modes map to subset selections (Strict = all; Standard = critical+important; Permissive = critical only)

**Deliverable:** L1/L2 auto-fix with backup + undo; ~80-150 total rules with full coverage of the 4 categories.

**Exit criteria:** User can apply 10 fixes on a sample project, then undo half of them, with no data loss; rule count meets the spec target of 80-150.

## Sprint 7 — Export + browser fallbacks (1 week)

**Goal:** Make the scan results portable. Polish the Firefox/Safari read-only experience.

**Key tasks:**

1. **PDF export**
   - Use `jspdf` or `pdf-lib` (lightweight, browser-only)
   - Layout: title page, summary, findings by section, code excerpts
   - Branded with the (placeholder) DecodeMind palette

2. **SARIF subset export**
   - Already a clean subset in V0; emit as `decodemind-report-{date}.sarif.json`
   - Validate against SARIF 2.1.0 schema (use `ajv` against the schema JSON)
   - V2 = full SARIF compliance — V1 ships subset with documented gaps

3. **Markdown export**
   - Plain-text-friendly report with sections, file:line refs, code fenced excerpts

4. **Firefox/Safari fallback polish**
   - The `<input webkitdirectory>` path is read-only (no write-back) — make this clear in UI
   - At end of scan, offer "Download patches as ZIP" containing modified files + a `apply.sh` script
   - Banner explanation on every scan in unsupported browsers

5. **Sharing report (without uploading code)**
   - "Copy summary" button: copies a Markdown snippet of just the summary + counts (no code) for sharing in tickets/Slack

**Deliverable:** 3 export formats + polished Firefox/Safari fallback.

**Exit criteria:** Export a scan in each format; reload the SARIF in VS Code's SARIF Viewer and verify it renders; Firefox user can do a full scan + download patches ZIP + apply them locally.

## Sprint 8 — Pre-launch polish + deploy (1 week)

**Goal:** Ship to production. Lighthouse audit, accessibility, deployment.

**Key tasks:**

1. **Lighthouse audit**
   - Target: Performance ≥ 80, Accessibility ≥ 90
   - Code-split heavy chunks (Prettier, ESLint browserify, WebLLM) — load on demand
   - Lazy-load each scanner worker by file-extension presence

2. **Accessibility pass**
   - Keyboard navigation (tab order, focus traps in modals)
   - Screen reader: ARIA labels on buttons, `aria-live` for progress
   - Color contrast audit (the brand palette is placeholder — finalize)
   - Touch targets ≥ 44×44 px (even though it's desktop-only, AA compliance)

3. **Branding pass**
   - Finalize the Tailwind palette (currently placeholder Slate/Blue) — decide if "DecodeMind" needs a unique visual identity beyond placeholder
   - Logo / favicon (SVG)
   - Open Graph meta tags
   - Loading splash (the first load is ~5 MB + model — make it not feel broken)

4. **Cloudflare Pages deployment**
   - Connect `v1` branch (or `main` after merge) to Cloudflare Pages
   - Configure custom domain (`decodemind.dev` — purchase domain if not already done)
   - Verify COOP/COEP headers are emitted in production (already in vite.config but Cloudflare may need a `_headers` file)
   - Test the full flow: visit → pick folder → scan → translate → apply fix → export

5. **Documentation**
   - Updated README with V1 features, screenshots, demo GIF
   - `docs/USAGE.md` for end users
   - `CONTRIBUTING.md` if going open-source
   - Blog post draft: "DecodeMind: a code scanner that runs entirely in your browser" — for the CV asset value

6. **Launch checklist**
   - All workers compile in production build (no broken inline data: URLs)
   - All 4 export formats work
   - Both Chrome and Firefox flows tested end-to-end
   - Lighthouse score meets thresholds on production deploy
   - Domain SSL works
   - 0 console errors on first scan

**Deliverable:** DecodeMind V1 live at `decodemind.dev` (or fallback domain). Public GitHub repo.

**Exit criteria:** A first-time user, given only the URL, scans their own code and successfully applies at least one fix.

## Out of scope for V1 (explicitly deferred)

Carried over from spec section 6, plus what V1 reaffirms as V2:

- L3 LLM-generated fixes (Qwen synthesizes patches): too fragile in 1.5B; revisit V2
- "Second opinion" via user's API key: new auth/network surface, V2
- Inline Monaco patch editor: heavy dep, V2
- More languages (Go, Rust, Java, C#, PHP): each is its own 2-3 week add, V2+
- VS Code / JetBrains extensions: V2 if there's demand
- `decodemind-scan` GitHub Action: V2
- Fine-tuned custom model: needs the V1 dataset first
- Team mode with shared rule library: V2 (B2B pivot)
- Interprocedural taint/dataflow analysis: ast-grep gap, V2
- Full SARIF 2.1.0 compliance: V1 ships clean subset, V2 expands
- Cross-file refactor: very complex, uncertain value

## Success criteria for V1 (revised from spec section 7)

**Technical (validated against Phase 0 measurements):**
- Default-tier scan of 10k-line project: ≤ 45 s on Intel i5 / 16 GB (revise if Phase 0 shows otherwise)
- <5% false-positive rate on author's own projects after `.decodemind-ignore` is configured
- Translation cache hit rate ≥ 60% after the 2nd scan of the same project
- Lighthouse Performance ≥ 80, Accessibility ≥ 90 on production

**Adoption:**
- Author uses DecodeMind on next 3 releases of own projects (dogfooding)
- 100 unique users in first month post-launch
- 10 qualitative feedback responses

**Product:**
- First-time user completes a full scan + applies at least one fix without external help
- 5 non-experts read 10 findings each and rate "Did this explain the problem clearly?" — ≥ 80% yes
- A re-scan of the `mamy` project after V1 launch surfaces the 4 actionable findings within the top 10 of the sectioned report (Phase 0 baseline: buried in 60-item flat list)
